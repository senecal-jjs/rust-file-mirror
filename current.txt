1. Fetch — find the starting point and everything since it.
Find the newest snapshot (this is what manifest::to_store/from_store already produce, generation-numbered — 
your existing snapshot mechanism). List log/ with start_after set to a cursor marking "everything already folded in." 
That cursor doesn't exist yet anywhere in State — you need something that remembers, per local root, which deltas 
have already been consumed on a prior sync, so a re-sync doesn't re-read and re-fold the entire log from the beginning 
every single time. A natural fit is a persisted string like "last delta key processed" (since your zero-padded keys 
already sort correctly, start_after on that exact key gives you exactly the new ones).

2. Merge — fold the fetched deltas onto the snapshot using the 4.4 rule.
Start from the snapshot's entries, then walk the deltas in listing order (already causally ordered). For each DeltaEntry,
 compare against whatever's currently accumulated for that path using the three-way rule: base_hash matches current → 
 fast-forward; content hash matches current → converge, pick canonical on (lamport, device_id); otherwise → conflict. 
 Two things fall out of this same walk as side effects, not separate passes: the highest lamport observed across every 
 entry read (fold into local via record_lamport — no increment yet, this is the "observed" half of the two-purpose pattern),
  and a list of unresolved conflicts discovered purely from other devices disagreeing with each other (distinct from the 
  conflicts your existing reconcile already finds between local and remote — both eventually need to land in the same place,
   worth deciding now whether that's one shared conflicts mechanism or two).

3. Bridge to what already exists.
reconcile(local: &[LocalEntry], baseline: &Baseline, remote: &Manifest) -> Plan (engine.rs:76) still expects a &Manifest — today's BTreeMap<String, ManifestEntry>. The merge in step 2 produces something richer (entries with lamport/device_id/base_hash/deleted). Decide here: either extend ManifestEntry itself to carry those fields (so the merged result is a Manifest, and reconcile needs no change), or keep DeltaEntry/Manifest as separate types and add a small conversion step before calling reconcile. Extending ManifestEntry directly is probably less friction, since reconcile doesn't actually need lamport/device_id/base_hash for its own logic — it just needs path/size/content_hash/object_key, same as today.

4. Reconcile — unchanged. Runs exactly as it does now, just fed the merged manifest from step 3 instead of one fetched with a single GET.

5. Apply — mostly unchanged, but now needs to collect outcomes. apply() already produces UploadResult/DownloadResult per action (execute.rs); it needs to additionally accumulate the outcomes of just the Upload and DeleteRemote actions (the ones that write to the remote — established a few turns back) into a list, since those are exactly what step 6 turns into delta entries. Everything else about apply — concurrency, resumability, progress — stays as-is.

6. Write — mint this device's own delta, if there's anything to say. If step 5's accumulated list is empty, skip entirely — nothing new happened, no delta needed. Otherwise: take the local Lamport counter (already caught up to the remote's max from step 2) and increment it once — this single value covers every entry in this sync pass's delta, since one sync pass is one causal batch. Build DeltaEntry rows from the accumulated outcomes (base_hash for each is whatever that path's content hash was in the merged manifest before this device's own change — what it believed was current when it edited). Call your existing log_delta to serialize, encrypt, and write it to log/{lamport:020}-{device_id}.delta, then persist the newly-minted value via record_lamport (the "just wrote" half of the two-purpose pattern) and advance the cursor from step 1 so this device's own delta doesn't get treated as new information on its next sync.

One thing worth double-checking once you're implementing step 6: log_delta right now takes state.get_latest_lamport() directly as the value to stamp the key with, without incrementing — worth confirming that's intentional scaffolding versus something to fix once the increment-at-write-time step lands.

Separately, not part of every sync: compaction (4.7) is a periodic maintenance operation, not a step in this cycle — some device, occasionally, writes a new snapshot from fully-merged state, verifies it reads back, then deletes superseded deltas older than a grace period. Worth treating as its own function entirely, triggered by delta count or a schedule, not something that runs inline with steps 1–6.






Here's the shape, sized to live in conflict.rs alongside the existing local-vs-remote conflict() stub — this handles the other source, merge-level RemoteConflicts.

Signature:


pub(crate) async fn resolve_remote_conflict<S: ObjectStore>(
    store: &S,
    conflict: &RemoteConflict,
    content_key: &SecretBox<[u8; 32]>,
    name_key: &SecretBox<[u8; 32]>,
    prefix: &str,
    state: &State,
    lamport: u64,
) -> Result<DeltaEntry>
Takes one conflict, resolves it, hands back the DeltaEntry describing the newly-published conflicted copy. The caller (build_plan, or a small pre-pass in sync()) loops over conflicts: Vec<RemoteConflict> and calls this once per entry — keeps the function itself testable against a single conflict, same pattern upload/download already use for single actions with apply() doing the looping.

Flow:

Compute the new name and its object_key. conflict_name(&conflict.loser.path, &utc_timestamp(), &state.device_name()?)? gives the renamed path; filename::object_key(name_key, &new_path)? derives its object_key the same deterministic way every other path does.

Fetch and decrypt the loser's original bytes. store.get(&format!("{prefix}{}", conflict.loser.object_key)).await?, then decrypt with content_key using the loser's original path as AAD — that's what it was encrypted under when it was first uploaded, so that's what has to be presented to authenticate it now.

Verify before trusting anything. Compare the decrypted content's BLAKE3 hash against conflict.loser.plaintext_hash. If they don't match, stop and return an error rather than publishing anything — this is exactly the "object key clobbered by a later write" scenario from a few turns back. Silently proceeding would publish wrong content under the conflicted-copy name; failing closed here mirrors what download() already does.

Re-encrypt under the new identity. Fresh nonce (never reuse), AAD is now the new conflicted-copy path, since that's the identity the new object is bound to. This produces the ciphertext to actually store.

Upload it. store.put_bytes(&format!("{prefix}{new_object_key}"), &new_ciphertext).await?.

Build and return the new DeltaEntry. path: new_path, object_key: new_object_key, plaintext_hash: conflict.loser.plaintext_hash (content's unchanged, just relocated), size: conflict.loser.size, mtime_utc: unix_timestamp(), deleted: false, deleted_at: 0, lamport (passed in — same value the caller mints for the rest of this sync, via the same max(remote_lamport, local_lamport) + 1 apply() already uses), device_id: state.device_id()?, base_hash: None — brand new path, nothing preceded it.

Integration point: the caller collects the returned entries across all conflicts, folds each into manifest under its new path (leaving the winner's entry at the original path untouched), and writes them to the log — either via their own log_delta call before apply() runs, or by extending apply()'s own deltas accumulator with them so they ride along in the same delta object as this sync's regular actions. Either works; a separate log_delta call keeps conflict-resolution writes cleanly independent of regular sync writes, which is probably the easier one to reason about first.

One limitation worth being upfront about: step 2 fetches the whole object into memory with a single get, which is fine for ordinary files but doesn't follow the multipart/streaming path large uploads already use elsewhere. Fine for a first version, but a large conflicted file would need the same chunked treatment upload.rs/download.rs already have, not a naive single-shot read.
